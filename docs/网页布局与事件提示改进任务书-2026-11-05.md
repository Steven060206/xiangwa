# 《箱娃》网页布局与事件提示改进任务书

- 日期：2026-11-05
- 适用端：电脑浏览器、手机竖屏、手机横屏
- 检查代码基线：`24a2506`
- 文档性质：两轮界面检查建议的合并交接文档；界面改进尚未实施。

## 1. 任务目标与执行边界

用户要求从真实玩家的操作体验出发，改善电脑端和手机端适配、页面布局、重要事件提示。本文件完整收录首轮11项建议及补充7项建议，供后续模型实施。

成功标准是让玩家容易回答以下问题：

1. 现在发生了什么，是否需要我操作？
2. 我当前可以做什么，下一步在哪里？
3. 我在哪个房间，选择的目标对应地图哪里？
4. 刚才的操作是否完成，为什么暂时不能继续？
5. 哪些信息只有我知道，哪些已经公开？

### 1.1 允许修改

- 页面空间分配、响应式布局、字号、间距、点击区域和视觉层级。
- 当前任务、行动、物品、地图、消息、公共信息之间的导航与展开方式。
- 弹窗、事件历史、未读提示、等待提示、提交反馈和错误呈现。
- 表单焦点、滚动位置、仍然有效的本地选择和输入内容的保留。
- 对现有合法行动、阶段和持续效果的准确解释与展示。
- 与上述改动相关的浏览器测试、界面模型测试和使用说明。

### 1.2 不在本次范围内

- 修改游戏规则、行动次数、阶段顺序、胜负条件、道具或能力效果。
- 修改信息可见范围、访问者与箱娃阵营权限、聊天接收范围。
- 调整四／五人模式、身份恢复、邀请码、撤销表决、存档或断线结束机制。
- 改动地图门、房间连接、角落定义、随机牌序或人机决策策略。
- 引入新的后端接口、存档格式、前端框架或大规模依赖迁移。
- 部署或重启正式服务，操作真实玩家房间或提交本机运行资料。

原则上使用已有过滤视图、事件数据和动作接口完成。若某个增强需要当前视图没有的信息，先采用不增加信息暴露的展示方案，不从其他玩家身份或服务端秘密状态补取。

## 2. 检查依据及证据强度

### 2.1 已实际体验的流程

在独立内存测试服务中创建五人房间，通过真实 Chrome 页面及手机触屏模拟体验了：

入席 → 大厅准备 → 抢选角色 → 初始道具 → 抽板与旋转摆放 → 箱娃秘密配置 → 翻无声标志 → 访问者窥探声明 → 箱娃确认 → 手记发现与夜视仪领取 → 事件回看 → 同房聊天 → 全体访问者投降结局 → 复盘入口。

电脑和手机分别查看了箱娃与访问者界面；复杂箱娃回合、死亡后交付遗物与箱人阶段尚需在实施验收中专门覆盖。正常操作使用页面按钮；其他座位及部分准备步骤使用测试服务已有动作接口推进，没有改动正式规则或真实存档。

手机证据来自 Chromium 的视口与触屏模拟，另执行过实际合成触摸拖动；不等于完成 iPhone Safari 或安卓手机实机验收。

### 2.3 如何理解后文的状态标记

- **已观察**：本轮在实际页面中看到或操作复现。
- **代码确认**：能从当前代码确认展示方式，但尚未对所有组合进行浏览器复现。
- **待验收**：为覆盖不同设备或复杂阶段而补充，不应当作已经发生的故障。

后文的尺寸目标和布局方案属于建议。可以采用达到同等体验的实现，但不能以压缩字号、隐藏合法行动或取消信息隔离来满足尺寸。

## 4. 建议的信息结构

### 4.1 电脑端

保留地图与操作并排。顶部显示当前任务，地图获得主要空间，右侧集中处理当前步骤。

```text
房间信息／连接状态／事件／房间操作
当前任务 · 行动者 · 我的身份与位置 · 回合
┌──────────────────────┬─────────────────┐
│ 楼层 · 定位自己 · 全图 │ 当前回应／行动  │
│                      │                 │
│        地图          │ 目标与选项      │
│                      │                 │
│ 角落信息按需查看      │ 当前步骤的按钮  │
└──────────────────────┴─────────────────┘
物品／能力、公共信息、消息、事件记录有稳定入口
```

### 4.2 手机竖屏

紧凑状态栏、可调整的地图区域和足够大的行动区域。小屏避免把地图与行动机械地各占一半。

```text
房间与连接状态／房间操作
当前任务 · 本人身份与位置
紧凑地图／当前位置摘要（可展开）
当前行动：类别 → 目标 → 必要选项
当前步骤的主操作
行动 ｜ 地图 ｜ 物品／能力 ｜ 消息
```

“固定主操作”只固定当前步骤确实存在的提交按钮，不人为创造统一的“下一步”动作。等待状态显示原因。打开地图、物品或消息后，返回行动应恢复合理位置及仍有效的输入。

### 4.3 布局约束

- 房间管理低频入口可以折叠；正在进行的投票、错误和必须回应的事件不能被藏入菜单。
- 手机地图展开时可成为主要区域，收起后恢复当前任务；继续保留现有专看地图能力。
- 底部固定导航和操作栏要计入布局，不能覆盖最后一项表单、消息或地图目标。
- 尽量减少同一操作路径上的嵌套滚动；无需强行禁止所有页面滚动。
- 布局以宽度、可用高度和当前任务共同决定，避免只按一个宽度阈值处理全部横屏场景。

## 5. 详细需求

### UI-01 手机空间分配与稳定导航

**问题与影响：**小屏操作区仅约160px，玩家需要通过窄窗口分段阅读一次结算。房间信息、撤销说明、当前任务和重复状态占去较多高度。

**建议实现：**

- 顶部压缩为房间信息与当前任务两层，保留身份、位置和回合。
- 将平时的撤销说明、结束和退出整理到房间操作入口；保留原权限与确认步骤。
- 撤销投票、待回应和异常状态出现时，单独展开任务提示，不要求先打开菜单。
- 手机提供行动、地图、物品／能力、消息的稳定导航；角色变化时名称准确更新。
- 小屏默认显示紧凑地图；根据任务切换展开地图或扩大行动区。
- 较长结算使用可滚动内容加稳定的主操作，保证底部内容不被遮挡。

**验收：**

- 375×667下，正常行动状态的操作区域争取约280px以上；若采用整屏行动页，以内容与主操作可同时到达为准。
- 当前待提交按钮不被导航栏、浏览器栏或软键盘遮住。
- 任务、地图和物品入口在不同阶段保持容易找到。
- 开菜单和切换视图不发送游戏动作，不解除撤销锁定。

### UI-02 电脑地图高度与信息层级

**问题与影响：**1366×768下顶部约占237px，地图下方默认展开的角落对照继续占位，宽屏仍只能看到地图的一截。

**建议实现：**

- 压缩重复的任务、身份及回合说明，保留一个主要任务说明位置。
- 保持左右布局，右侧先显示当前回应、结算或行动。
- 角落对照默认收起；选中角落时显示编号和完整名称。
- 物品、能力、公共资料和消息提供入口，不作为当前操作前的长列表。
- 保留舒适阅读宽度，不把操作栏压窄到长选项不断换行。

**验收：**

- 1366×768常规窗口下，地图绘图区争取至少约380px高。
- 1280×720仍能方便地同时看地图与当前操作；1920×1080不出现不必要的大块空白或过长行文。
- 查看角落对照不会让当前确认按钮无法到达。

### UI-03 行动分类与滚动衔接

**问题与影响：**手机点击“前往操作”后，只先看到移动选项，窥探在下面；关闭窥探结果后，旧滚动位置可能让结果标题消失。

**建议实现：**

- 在行动顶部清晰呈现移动、窥探、道具等当前合法类别，再展开具体目标。
- 标准行动与自由行动分组，保留各自现有可用条件。
- 本人提交后进入新结算步骤时，将操作区定位到新步骤标题。
- 结果提示的“前往处理”定位待处理步骤；纯关闭只收起提示。
- 普通同步不抢走阅读位置；从物品或聊天返回时恢复当前步骤。
- 保留仍有效的输入和选择；目标失效时说明原因并让玩家重新选择，不能悄悄改选另一个目标。

**验收：**

- 无需向下试探滚动，就能知道当前有哪些行动种类。
- 窥探后能连续理解“发现内容 → 选择处理方式 → 确认”。
- 查看物品再返回行动不丢失仍有效的选择。
- 普通他人动作、在线变化及重复同步不反复跳到顶部。

### UI-04 重复事件与可见范围说明

**问题与影响：**一次手记发现同时显示“手记已公开／全员可见”和“你发现手记／仅你可见”，重复解释容易混淆公开内容和发现位置。

**建议实现：**

- 同一次手记发现与自动公开合并为清楚的结果卡，避免重复整段卡面效果。
- 分别说明物品内容、发现位置等信息的可见范围，不给混合内容只套一个笼统标签。
- 区分“对应能力说明”“能力已设置”“能力正在生效”，不能看到卡面就误示发动。
- 所有文本取自本人过滤后的状态与已核对说明。

**示例文案，需按实际状态组合：**

> 发现手记10 · 已自动公开
>
> 对应能力：NO.10 鬼来电
>
> 手记内容全员可见；发现位置仅你知道。
>
> 下一步：选择补位方式，并完成当前可用的道具选择。

**验收：**

- 一次发现没有重复的主要说明。
- 公共消息与其他玩家视图不增加发现角落或其他私密信息。
- 卡面介绍不会被理解为未发动能力已经生效。

### UI-05 提示分级、后续操作与事件历史

**问题与影响：**多种事件都使用模态弹窗，玩家反复经历读提示、关闭、寻找下一步；“最近事件0”容易被误认为没有历史。

**建议呈现：**

| 类别 | 典型情境 | 展示方式 |
| --- | --- | --- |
| 需要本人回应 | 行动确认、灭火器、交换、撤销投票 | 常驻任务提示，明确下一步，提供定位入口 |
| 重大状态变化 | 死亡、阵营变化、胜负 | 强提示，说明变化与接下来可做的事 |
| 关键发现或私密结果 | 窥探、手机查看、重要线索 | 结果卡，明确可见范围，可回看并定位结算 |
| 常规成功反馈 | 一般物品入库、已完成操作 | 较轻提示并写入本页事件记录 |
| 普通轮次变化 | 轮到自己、进入下一阶段 | 更新任务栏并简短强调，不强制弹窗 |

- 事件卡根据情境提供“前往处理”“查看物品”“查看复盘”，另保留关闭方式。
- 导航按钮只负责定位，关闭、Esc和外侧点击不执行结算、不穿透。
- 手机将主要入口放在容易触及的位置，不只依赖右上角小字关闭。
- 事件入口改为“事件”配未读角标；没有未读时隐藏数字，历史仍可访问。
- 本次无需新增跨刷新事件存储；保留首次快照静默和已有回看边界。

**验收：**

- 从需要处理的事件到待办控件至多一次导航。
- 普通成功提示不会频繁阻断连续操作。
- 已读清零不会让玩家误以为历史被删除。
- 刷新、撤销和重复同步不会生成虚假的获得提示。

### UI-06 聊天入口与未读提示

**问题与影响：**消息到达时，玩家停留在行动区无法察觉；聊天位于侧栏长内容之后。

**建议实现：**

- 电脑提供稳定消息入口，手机导航提供消息入口和未读数量。
- 点击后直接显示当前可用频道和消息，不要求先滚过所有物品与资料。
- 输入框附近持续显示同房／箱娃阵营及实际接收范围。
- 关闭聊天返回原行动位置；软键盘出现时输入框和发送按钮仍可到达。
- 未读只基于当前身份实际收到的消息；保持现有换房、频道变化和历史接收规则。

**验收：**

- 在地图或行动区收到同房消息时，有可见的新消息标记。
- 打开消息和返回行动各需一次明确点击。
- 切换频道后不误发给旧接收范围，不因界面改造向其他玩家展示消息。
- 撤销投票时聊天与地图浏览保持现有允许行为，不影响表决状态。

### UI-07 地图定位、目标联动与触屏点按

**问题与影响：**准备结束后手机仍停留在此前查看的地下室，人物已在一楼；位置入口和角落点击区域偏小。

**建议实现：**

- 准备进入探索时，自动定位本人当前楼层一次；之后尊重玩家手动浏览。
- 将按本人名字定位的现有能力提供为更明确的“定位自己”入口。
- 提供查看全图与定位当前房间的视图，保留拖动、楼层切换和专看地图。
- 操作列表选中目标时，地图对应公开房间或本人可知角落高亮；地图选中角落时显示完整名称。
- 常用触控入口争取44×44px；小图案可扩大点击区域，相邻角落不能因区域重叠而点错。
- 五人同房时压缩重复的位置文字，保留座位号、本人标识及完整信息的查看方式。
- 旋转不改变角落编号，编号文字保持正向。

**验收：**

- 新进入探索可立即辨认本人位置；浏览其他楼层不会被每次同步强行拉回。
- 定位后尽量展示对应地图板及周围关系，不只把棋子贴在边缘。
- 角落选择、操作列表和名称对照一致。
- 访问者不会从新增高亮、定位按钮或地图变化获得隐藏位置。
- 在真实触摸拖动与点按中验证地图滚动，不仅查看缩小后的截图。

### UI-08 手机横屏布局

**问题与影响：**667×375时操作区位于首屏下方；844×390时地图高度仍明显不足。

**建议实现：**

- 横屏压缩房间信息和任务栏，优先给地图与当前操作空间。
- 宽度足够采用左右布局；不足时使用清楚的地图／行动切换。
- 低高度收起完整席位名单、角落对照和参考说明。
- 当前任务和返回行动保持容易到达，必要时允许页面自然滚动。

**验收：**

- 667×375、844×390首屏均有明确当前行动入口。
- 不需要先滑过整块地图才能找到唯一的确认按钮。
- 横竖屏切换后选择、输入、弹窗和地图位置保持合理状态。
- 所有内容可到达，无整页横向溢出。

### UI-09 入席与大厅准备

**问题与影响：**加入朋友的入口排在建房表单之后；五人大厅席位较高，主要操作靠近手机底部。

**建议实现：**

- 明确区分创建与加入入口，共用昵称但避免把建房人数作为加入流程的前置内容。
- 通过邀请链接进入时，优先展示目标房间、昵称和加入动作。
- 手机缩短开场介绍，装饰与详细说明放到主要操作之后。
- 大厅压缩席位高度，突出本人准备状态、未准备者与当前人数。
- “准备”和房主“开始游戏”位于稳定位置，仍遵守全员准备后的既有流程。
- 四人和五人、真人与人机混合都使用相同清楚的席位表达。

**验收：**

- 邀请进入时，不需经过创建房间内容才能找到加入按钮。
- 五人大厅能快速看清自己是否准备、接下来由谁操作。
- 人数选择、邀请码验证、身份恢复、补齐人机与抢选时机保持不变。

### UI-10 道具浏览与选择

**问题与影响：**12种道具采用长列表；比较后面的道具需要记住前面内容，且页面重复说明当前任务。

**建议实现：**

- 电脑可用两列紧凑卡片，手机用清晰列表。
- 默认展示名称与准确的核心用途，完整效果可展开；关键限制不能被摘要误述。
- 去除任务栏和列表内部重复的整段指引。
- 点击选择后明确高亮，在稳定位置显示“领取××”；浏览详情不等于领取。
- 简洁显示当前选择者和已领取进度，其他玩家等待状态清楚。
- 已领取内容仍可查看完整效果。

**验收：**

- 玩家浏览列表后半段时仍能知道选中的是哪件道具。
- 查看、选择和实际领取的区别明确，不因点开详情提交选择。
- 多人同步后已不可领取的道具不会继续显示为可提交；轮次与候选池不变。

### UI-11 结局与复盘入口

**问题与影响：**结局提示明确，但完整复盘位于库存、公共信息和其他记录之后，需要长距离滚动。

**建议实现：**

- 结局卡直接提供完整盘面、玩家物品和行动记录的入口。
- 结束后的“查看进度”改成更具体的“查看复盘”。
- 终局列表与地图联动，点击角落或记录定位对应位置。
- 房主再开一局与复盘入口分开，说明将返回大厅重新准备。
- 仅在已有终局公开状态下显示完整信息，不扩大进行中可见范围。

**验收：**

- 关闭胜负提示后，一次点击能进入复盘。
- 手机无需穿过长库存列表寻找完整盘面。
- 正常结局、被房主结束、玩家退出等状态沿用各自已有行为，不混为一种复盘流程。

### UI-12 等待与操作不可用的原因

**现状：**页面已有等待文案及禁用控件。补充目标是让不同原因在操作位置可辨认，并检查所有回应组合。

**建议实现：**

| 状态 | 建议反馈 |
| --- | --- |
| 他人回合 | 当前行动者及本人可以查看的内容 |
| 声明已提交 | 等待对应玩家确认，显示已有权限知道的声明摘要 |
| 请求处理中 | 正在提交，并保留本次动作说明 |
| 撤销投票 | 投票进度、本人的回应按钮、可公开的待回应者 |
| 断线 | 正在恢复连接，当前画面可能尚未更新 |
| 人机暂停 | 暂停原因及原有权限允许的继续入口 |
| 目标不再合法 | 当前进度已变化，请重新选择目标 |

- 不为解释禁用原因而暴露未公开持有者、能力、库存或潜伏信息。
- 手机投票区域不依赖长横向滚动才能找到同意和拒绝。
- 取消、拒绝与继续当前进度的含义清楚，原有权限不变。

**验收：**

- 玩家能从当前操作区知道为何不能操作、是否还需要自己回应。
- 等待期间仍可使用原本允许的地图、物品、事件和聊天入口。
- 打开本地面板、切楼层或定位玩家不解锁游戏按钮。

### UI-13 提交、网络异常与恢复反馈

**现状：**已有断线横幅、自动重连与操作禁用；操作错误主要显示在页面顶部。

**建议实现：**

- 在触发动作附近显示“正在提交”等状态，不只让所有按钮突然变灰。
- 区分服务器明确拒绝、尚未确认结果和已收到成功状态。
- 结果不明时提示正在确认最新进度，不先宣告成功或失败，不自动重复发送原游戏动作。
- 错误在当前操作附近可见，保留顶部全局提示作为补充。
- 恢复后明确显示当前任务与必要的恢复反馈，避免重播旧库存事件。
- 错误或断线横幅出现时，重新核对固定高度布局，不把底部控件挤出可到达区域。

**验收：**

- 慢响应、服务端拒绝、提交期间断网、恢复连接分别有准确反馈。
- 重复点击不会造成多次动作；复用现有请求与版本控制，不改变规则协议。
- 合法的未提交输入尽量保留，过期目标明确作废，不暗中替换。
- SSE与轮询两种同步方式下，恢复状态与操作提示一致。

### UI-14 持续效果的常驻提醒

**现状：**持续效果已有文字展示，但分散在能力与公共资料中；玩家读过发动弹窗后可能忘记。

**建议实现：**

- 在当前行动附近提供紧凑的“当前影响”区域。
- 展示本人可见的生效效果、对当前操作的影响，以及已确定的解除条件或结算时机。
- 例如封门、鬼来电、铃的限制、等待结算的能力，均依据当前状态呈现。
- 有多个效果时显示简洁摘要，展开查看详情。
- 已解除效果及时移除；未发动的卡面介绍不混入“正在生效”。

**验收：**

- 受影响玩家不打开事件历史也能知道当前行动受何影响。
- 不虚构剩余回合、计时或未公开效果，不计算与服务器规则不一致的新状态。
- 现有规则测试与效果终止边界继续通过。

### UI-15 箱娃、遗物交付与箱人指引

**现状：**本次主要浏览了箱娃开局与确认访问者行动；手机复杂箱娃阶段及死亡后的路径需专项验收。

**建议实现：**

- 按现有状态区分箱娃准备、能力处理、潜伏，突出当前步骤。
- 哭喊等可选事项明确标为可选；步骤条不能强制新增顺序或把可选动作变成必做。
- 能力手牌、设置栏、发动入口及原因说明相互靠近，减少来回查看长列表。
- 死亡后若仍需交付遗物，优先显示交付待办；身份变化与阶段文案依据实际状态更新。
- 交付完成后明确告知作为箱人何时行动、等待谁、可查看什么。
- 箱人已完成潜伏、正在等待及被消灭后的界面分别准确表达。

**验收：**

- 手机箱娃能完成合法的哭喊、设置／回收、发动与潜伏流程。
- 跳过可选步骤仍可按原规则继续；不新增强制确认或多消耗动作。
- 死亡、继承、箱人行动与被消灭后都能找到当前合法入口。
- 不因使用统一布局而把箱娃的能力或移动范围提供给箱人。

### UI-16 连续事件与多人同步稳定性

**代码确认：**新突出事件会追加到已经打开的弹窗内容中，连续事件可能让内容越来越长。

**建议实现：**

- 普通事件排队或合并摘要，避免正在阅读的正文频繁变化。
- 需要本人处理的事项使用清楚的优先提示，不让旧的一般通知挡住回应入口。
- 每条事件保留自身可见范围；同一弹窗中的公开与私密内容分清。
- 长内容下关闭、前往处理和事件切换仍容易到达。
- 普通同步不重置正在输入的文本、有效选项或阅读位置。
- 阅读历史事件时标明历史性质，不把已处理事件继续表现为待办。

**验收：**

- 同一快照的多事件、跨多个快照的连续事件和重大状态变化都能读完并返回游戏。
- 重复同步不重复计数，撤销不误报新获得。
- 已失效的待办导航指向当前实际状态，不执行旧动作。
- 轮询、SSE及在线状态更新下，当前表单行为稳定。

### UI-17 字号、缩放、长内容与键盘操作

**现状：**不少辅助内容使用11—12px，已有基本键盘焦点样式；扩大字体和复杂内容需继续验收。

**建议实现：**

- 当前任务、效果和结算说明使用更舒适的字号与行高，优先考虑14—16px阅读正文。
- 次级文字可以较小，但不能靠继续缩字解决布局拥挤。
- 状态使用文字配合颜色、边框或图标，不只靠红绿区分。
- 长昵称与长能力名不覆盖按钮，必要时换行并提供完整查看方式。
- 保留语义化按钮、标签、焦点指示和对话框键盘行为。
- 关闭弹窗后把焦点交还合理入口；原控件已消失时定位当前步骤。

**验收：**

- 电脑125%、150%缩放下主要任务与操作可用。
- 手机较大系统字体、长昵称、长说明、较多库存与多条消息不造成关键内容截断。
- 使用Tab、Enter、Space、Esc能完成主要导航与确认；不会卡在不可见控件。
- 不将触控模拟结果表述为已通过完整可访问性标准认证。

### UI-18 真机键盘、浏览器栏与安全区域

**状态：待验收。**这些不是本次已经确认的故障，而是响应式改造必须补齐的场景。

**建议实现与验收：**

- 昵称、邀请码及聊天输入时，软键盘不挡住输入内容和必要提交入口。
- 地址栏展开、收起时，地图与操作区不发生妨碍阅读的跳动。
- 固定底部导航与按钮避开手机手势区域，内容末尾保留正确空间。
- 从聊天软件切回游戏后，连接状态、当前任务与过期选择能够正确恢复。
- 分别验证 iPhone Safari、安卓常用浏览器的弹窗、滚动、横竖屏和触摸拖动。
- 不依赖桌面鼠标悬停才能理解关键控件；不禁用用户缩放来掩盖布局问题。

没有实机条件时，交付中明确列出未完成的实机项；不能用 Chromium 改视口替代并宣称全部通过。
